# MES Copilot

An MES copilot for small and mid-size manufacturers, built for the **Meta Global AI Developer Hackathon** (Cerebral Valley, Startup track, Push the Frontier theme) by Tré Wright / One Cube Up LLC.

Small plants lose thousands of dollars per minute to unplanned downtime, but their production knowledge lives in operators' heads and their downtime records are free-text notes nobody can trend. This copilot fixes that with three flows:

1. **Vision QC** — an operator photographs a part and gets a defect check (pass / flag, defect types, confidence, plain-language note, suggested disposition: use / rework / hold). Labeled demo-grade assist, not a certified inspection.
2. **Downtime Detective** — an operator describes a stoppage in plain language ("press kept jamming on the left feed, cleared it 3 times then called maint") and gets a structured record in the format a plant actually files: line, equipment, downtime category + cause code, estimated duration, root-cause draft, corrective-action draft. Saved to the event list and counted in the dashboard.
3. **Ask Production + Shift Handoff** — a supervisor asks plain-English questions ("What stopped Line 2 this week, and what did it cost?", or a plain "How is Line 1 doing today?") and gets answers whose **numbers are all computed in code** from the production data; the model only phrases them. Plus a one-click shift-handoff summary for the current shift.

## The one rule that matters

Models never calculate. Every figure in Flow C and the handoff is computed deterministically in `src/server.js` from the dataset and handed to the model as a facts block; the prompts in `src/prompts.js` forbid the model from adding, rounding, or inventing any number, and require it to say plainly when the facts don't cover a question.

## Data (clean room)

Everything runs on a **fully synthetic dataset** for a fictional two-line plant, "Riverbend Fabrication — Plant 1," generated by a seeded script (seed 42, byte-identical every run) and modeled only on public ISA-88 / ISA-95 structures. No real company data, code, screenshots, or documents are used anywhere — see `../SYNTHETIC-DATA-SPEC.md` and `../BUILD-PLAN.md`.

Dataset volumes: 2 lines · 6 work units · 5 SKUs · 14 operators · 180 shift instances · 301 orders · 491 downtime events · 898 inspections · 40 quality holds over 30 days (2026-10-05 → 2026-11-03; the demo "today" is the final day, with a shift still mid-run for the handoff). Planted story patterns a judge can find: Line 1 jams cluster on second shift, a week-3 supplier lot drives a defect spike, Thursday changeovers run long, and one big breakdown lands each week.

## Run it

```bash
npm install
npm run generate-data        # builds the synthetic dataset into data/ (seeded, reproducible)
node src/generate-samples.js # builds the bundled Vision QC sample photos into public/samples/
npm start                    # http://localhost:3000  (PORT env overrides)
```

### Stub mode vs live mode

- **No `META_API_KEY` set → STUB mode.** The whole app runs end to end with deterministic mock responses in the exact same shapes as the live API path — JSON payloads carry `"_stub": true`, text answers carry a `[STUB MODE]` prefix, and the UI badge says so. Stub vision verdicts for the bundled samples match their seeded defects; stub verdicts for uploaded photos say plainly that stub mode cannot truly inspect a photo.
- **`META_API_KEY` set → LIVE mode.** Calls go to the Meta Model API (Llama API):
  - Base URL: `https://api.llama.com/v1` (OpenAI-compatible `POST /chat/completions`), override with `LLAMA_API_BASE_URL`.
  - Text model (Flows B + C): `Llama-4-Maverick-17B-128E-Instruct-FP8`, override with `LLM_TEXT_MODEL`.
  - Vision model (Flow A): `Llama-4-Scout-17B-16E-Instruct-FP8`, override with `LLM_VISION_MODEL`.
  - Model IDs are from Meta's model list (llama.developer.meta.com/docs/models); both Llama 4 models accept text + image input.
  - See `.env.example`. The key is read from the environment only and is never committed. Sample-photo verdicts are cached server-side to save credits.

## Layout

- `src/server.js` — Express server: loads the dataset into memory at boot, serves the API + UI. All arithmetic lives here.
- `src/llm.js` — Meta Model API client (live) + deterministic stub (no key).
- `src/prompts.js` — the three flow prompts and the taxonomy they share.
- `src/generate-data.js` — seeded synthetic-dataset generator → `data/*.json`.
- `src/generate-samples.js` — generates the bundled synthetic sample part photos.
- `data/` — generated dataset (JSON). Stoppages filed through Flow B persist to `data/user_downtime_events.json`.
- `public/` — one-page vanilla JS app: dashboard snapshot + the three flow panels; phone-friendly.

## API

| Route | What it does |
|---|---|
| `GET /api/health` | Status, LLM mode/models, dataset counts |
| `GET /api/snapshot` | Today's orders, downtime minutes + cost, open holds |
| `POST /api/downtime` | Flow B: `{description}` → structured record, saved |
| `GET /api/downtime/recent` | Stoppages filed through Flow B |
| `POST /api/ask` | Flow C: `{question}` → computed facts + phrased answer |
| `GET /api/questions` | The 8 seeded judge questions (UI chips) |
| `POST /api/handoff` | Shift handoff summary (computed facts, model-phrased) |
| `GET /api/samples` | Bundled Vision QC sample photos |
| `POST /api/qc` | Flow A: `{sampleId}` or `{imageBase64}` → verdict JSON |
